# 部署与运维

## 1. 服务器规格

| 场景 | 建议 | 说明 |
|---|---|---|
| 演示 / 5 人以内 | 2 核 2 GB | Kaizen 常驻约 150–300 MB（含 DBOS 与 SQLite），加 Nginx；RSI 会话期间 CPU 会短时打满 |
| 车间 / 部门级 | 4 核 8 GB，50 GB SSD | 推荐 |
| 私有化大模型 | 另配 GPU 服务器（vLLM/SGLang 部署 Qwen3.8 等） | Kaizen 只需改 `LLM_BASE_URL` |

## 2. Docker Compose 部署

```bash
cd kaizen-agent/deploy
cp .env.example .env && chmod 600 .env
# 生成 KAIZEN_API_KEY 写入 .env（openssl rand -hex 32）
# 可选：填写 LLM_API_KEY（DeepSeek 或 DashScope）；不填则用离线的统计 + 贝叶斯内核
docker compose up -d --build                  # Kaizen + Nginx
docker compose ps
```

- 打开 `http://<服务器>/` 即 Kaizen 控制台：主区域是对话，左侧栏是新对话、功能（质量总览 / 案例库 / CAPA 看板 / 自我进化 / 改进周期 / 审计日志）和最近对话。
  `KAIZEN_DASHBOARD_PUBLIC=false` 时，首次写操作会提示输入 `KAIZEN_API_KEY`。
- 首次启动时服务器约 2 秒就可用；演示数据在后台生成，控制台顶部显示进度（v0.6 加入 harness 后实测约 2.7 分钟，测量时机器负载约 20；v0.5 空闲机器约 40 秒；2 核云服务器会更久）：
  按时间回放去年至今的演示历史（含 11 次历史 RSI 会话、每个历史案例的快慢双脑、4 个可靠度训练窗口、1 次 RRSI 策略进化），同时在独立进程里跑冷启动基准（4 个种子 × 6 种模式），最后跑今天的在线 RSI 会话、训练窗口、策略进化和孪生对照。
  中途重启会从断点继续（回放没做完就重来，后面的步骤缺什么补什么）。之后再启动约 2 秒。
- `KAIZEN_SEED_BACKGROUND=false` 改为等演示数据生成完再开始服务（测试里这样用）；`KAIZEN_RSI_WORKERS` 设置练习题的并行进程数（默认 CPU 核数 − 2，最多 8，0 = 不用进程池）。
- 不需要 MCP 客户端接入时设 `KAIZEN_ENABLE_MCP=false`。

### RSI 配置

| 变量 | 说明 |
|---|---|
| `KAIZEN_RSI_ON_STARTUP` | 首次写入演示数据后自动跑冷启动基准与一次在线探索 |
| `KAIZEN_RSI_CURRICULUM_MODEL` | 课程 agent 用的模型（例如 `qwen4-max`），留空则与执行 agent 相同；对应论文中“执行与课程/验证用不同模型家族” |
| 在线会话 | 对话里选“自我进化”模式发送，或左侧栏「自我进化」→「启动自我进化会话」，或 `POST /api/rsi/sessions`；孪生经验权重 0.5 |

> 孪生的根因分布与机台热点目前是演示用的虚构值（`backend/app/rsi/twin.py`）。真实部署前应当用本厂历史数据校准，否则 RSI 学到的是孪生而不是产线。

## 3. 升级说明

**从 Kaizen v0.1（多行业版）升级**：v0.2 数据结构不兼容，首次启动会把旧的 `kaizen.db` 自动改名为 `kaizen.db.v1.bak` 后重建（不删除）。

**从 v0.4 升级到 v0.5**：数据结构不变，直接替换代码即可。v0.5 删除了 Open WebUI 相关的一切：`/v1` OpenAI 兼容接口、
`KAIZEN_OPENWEBUI_URL`、`KAIZEN_ENABLE_OPENWEBUI_COMPAT`、compose 里的 `open-webui` 服务和 `scripts/dev-openwebui.sh`。旧 `.env` 里的这些变量会被忽略，可以删掉。
浏览器里的对话记录从 sessionStorage 改为 localStorage 多会话保存，升级后旧的单条对话不再显示。

## 4. 本地开发

```bash
# 后端 + 控制台（自动建 venv；未配置 KAIZEN_LLM_API_KEY 时为离线的统计 + 贝叶斯内核）
./scripts/dev-backend.sh            # http://localhost:8000

# 测试
cd backend && .venv/bin/python -m pytest -q
```

接入真实大模型：

```bash
KAIZEN_LLM_API_KEY=sk-xxx KAIZEN_LLM_MODEL=deepseek-v4-pro ./scripts/dev-backend.sh
```

## 5. 运维要点

| 项 | 做法 |
|---|---|
| 备份 | `kaizen-data` 卷：业务库 `kaizen.db` 与 DBOS 系统库 `kaizen-dbos.sqlite`（WAL 模式，热备用 `sqlite3 <db> ".backup x.db"`）；对话记录只在用户浏览器里 |
| 日志与轨迹 | 容器日志限制 10 MB × 3；每次分析的步骤耗时、token 用量与 DBOS workflow_id 在 `analysis.trace`，步骤明细见 `GET /api/workflows/{id}/steps` |
| 崩溃恢复 | 分析中途重启时，DBOS 在启动时自动从最后完成的步骤继续，不重复调用大模型 |
| 学习监控 | 「自我进化」→「持续学习」页：若“持续学习”曲线持续低于“冻结先验”，说明确认的根因标签有问题或工艺发生了漂移，应复核近期关案 |
| 成本 | 每个案例约 4–6 次模型调用；`deepseek-flash` 成本最低，`deepseek-v4-pro` 推理质量更好 |
| 健康检查 | `GET /healthz` |
| 接入 MES/YMS/FDC | 用只读适配器替换 `backend/app/fab/simulate.py` 的数据来源（数据结构见该文件）；异常事件 `POST /api/cases`，随后 `POST /api/cases/{id}/analyze?stream=false`；工程师确认根因 `POST /api/cases/{id}/close` |
